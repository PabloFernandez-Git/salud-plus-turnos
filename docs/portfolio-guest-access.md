# Acceso invitado de portfolio (preparado localmente)

`PORTFOLIO_GUEST_ACCESS_ENABLED=false` conserva el login actual. El nuevo flujo solo se muestra cuando esta variable y `PORTFOLIO_DEMO_MODE` son `true`. El navegador reutiliza una sesión Supabase existente; si no la hay, llama a `signInAnonymously()` directamente a Supabase y la cookie SSR permite abrir el centro. No habilitar el flag ni Auth anónimo hasta completar todos los pasos siguientes. El flag controla la interfaz; la configuración de Supabase Auth es la barrera de registro real.

La migración **solo DEMO** `supabase/demo/migrations/20261103130000_portfolio_guest_access.sql` exige el único centro ficticio y los grants de solo lectura anteriores. Instala un hook `portfolio_allow_anonymous_signup(jsonb)`, un trigger `auth.users` que rechaza altas no anónimas y provisiona cada invitado, y policies restrictivas para que un invitado vea solo su perfil y membership. El marcador sintético del perfil mantiene esa restricción aunque Auth cambie luego el claim `is_anonymous`. El trigger limita a 500 invitados simultáneos y solo crea filas en el centro `d0000000-0000-4000-8000-000000000001`. `auth.users.email` sigue NULL; `public.users.email` usa un identificador ficticio `guest+<uuid>@guest.salud-plus.invalid` para satisfacer su columna `NOT NULL`. Es una excepción exclusiva de DEMO a la proyección habitual de email. La pantalla de usuarios para el invitado muestra solo su propia fila; los otros módulos de consulta mantienen las lecturas ADMIN existentes. No se conceden INSERT/UPDATE/DELETE ni RPC nuevas al cliente.

## Activación manual posterior, solo DEMO

`supabase/demo/auth-config.example.toml` documenta los valores de Auth exclusivamente para DEMO; es una referencia que no carga la CLI. Comprobar cada ajuste en el Dashboard/Management API del proyecto DEMO. La activación sigue siendo una operación posterior y separada.

1. Confirmar por referencia de proyecto `oygrwetmxsqgcizopezq`, inventario de un centro, 28 migraciones previas, RLS y los grants de solo lectura con una transacción read-only. Aplicar **solo** la migración invitada tras aprobación separada. No usar `db push` sin revisar que no incluya migraciones ajenas.
2. En Authentication > Hooks, seleccionar `Before User Created` → función PostgreSQL `public.portfolio_allow_anonymous_signup`. Confirmar `EXECUTE` solo para `supabase_auth_admin`; probar que el hook acepta `is_anonymous=true` sin email/teléfono y rechaza `false`. El trigger de base rechaza igualmente altas no anónimas si se desconfigura el hook.
3. Mantener deshabilitados los proveedores de signup por email, teléfono y OAuth no usados; no activar enlace manual de identidades. Para permitir `signInAnonymously`, Supabase Auth necesita permitir nuevas altas globalmente: habilitarlo **solo después** del hook y del trigger, y entonces habilitar Anonymous Sign-Ins. Intentar altas por email y teléfono mediante la API y comprobar rechazo y cero filas nuevas. La cuenta DEMO actual puede permanecer para operación, sin divulgar su contraseña.
4. Configurar `Authentication > Rate Limits > Anonymous sign-ins` inicialmente en **5 por IP por hora**. Vigilar usuarios anónimos, Auth/DB y MAU; si se agota el cupo o hay tráfico distribuido, desactivar Auth anónimo antes de elevar límites. El límite SQL de 500 es la última barrera, no un control de tasa. Supabase recomienda CAPTCHA para altas anónimas.
5. Si se activa CAPTCHA en Supabase Auth, configurar Cloudflare Turnstile para el dominio canónico, cargar su **site key pública** en `NEXT_PUBLIC_PORTFOLIO_TURNSTILE_SITE_KEY` y poner `PORTFOLIO_GUEST_CAPTCHA_REQUIRED=true`. El login falla cerrado si se exige CAPTCHA sin site key. Verificar que el botón queda deshabilitado sin token y que Auth rechaza un alta directa sin token. No configurar la secret key de Turnstile en Vercel: va solo en Supabase Auth. Revisar además el efecto de CAPTCHA sobre el login de la cuenta operadora.
6. Con dos navegadores aislados, confirmar UUID/sesión diferentes, recarga que reutiliza sesión, lectura de centro/dashboard/agenda/turnos/pacientes/profesionales/especialidades/disponibilidad/usuarios/configuración, cero perfiles/memberships del otro invitado, cero lecturas de otro `center_id` y rechazo de DML y RPC sensibles con ambos JWT. Comprobar que un usuario anónimo no tiene `platform_admins`.
7. Recién después del smoke de Auth, RLS, lecturas, negativos y abuso, configurar `PORTFOLIO_GUEST_ACCESS_ENABLED=true` en el despliegue DEMO y desplegar por autorización separada. Nunca cambiar las variables de DEV ni `main`.

## Limpieza controlada

Ejecutar `supabase/demo/cleanup-guests.sql` como operador **solo en DEMO**. Selecciona como máximo 100 cuentas Auth anónimas de más de 30 días, con perfil sintético y única membership ADMIN en el centro DEMO; excluye admins de plataforma. Muestra UUID/fecha y borra en orden FK `center_memberships` → `public.users` → `auth.users`, dentro de una transacción que termina en `ROLLBACK`. Revisar el lote y los tres conteos; cambiar el `ROLLBACK` final por `COMMIT` únicamente para el lote aprobado. Verificar después que no quedan filas de esos UUID y que la cuenta operadora y los datos ficticios permanecen. La limpieza no revoca instantáneamente un JWT emitido, pero sin perfil ni membership ya no accede a las lecturas tenant.
