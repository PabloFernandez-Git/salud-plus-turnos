## 2. Contratos del dominio

- Availability pertenece a ProfessionalCenter; weekday ISO: 1=Lunes, 7=Domingo. Intervalo [start_time,end_time), hora local de centers.timezone. La UI y Zod aceptan HH:MM 00:00–23:59, precisión de minuto, sin 24:00 ni cruce de medianoche en una fila. Permiten dos franjas contiguas y varias no superpuestas el mismo día.
- Sólo se presentan filas is_active=true. “Quitar horario” deja is_active=false; no DELETE, reactivación ni histórico en esta tarea. Crear nuevamente inserta una fila nueva.
- Una franja se edita sólo en sus horas, no se mueve de día desde el formulario inline. Para moverla: quitar y crear otra. La duración habitual se guarda en professional_centers.usual_appointment_duration_minutes, 5–480, múltiplo de 5, default DB 30.
- Mutaciones de horario no cambian appointments. Después de cada create/update/deactivate exitoso, la respuesta indica si existen appointments futuros bloqueantes fuera de cualquier franja activa del ProfessionalCenter. La UI advierte sin ofrecer cancelación/reprogramación. Una duración distinta no cambia por sí sola las franjas ni dispara esa advertencia.
- Profesional/Center inactivos no ofrecen disponibilidad operativa. Admin/Reception sólo acceden a ProfessionalCenter activos desde este módulo; Professional debe estar vinculado a su ProfessionalCenter activo.
- Si otra operación reactiva un ProfessionalCenter, las franjas de Availability que seguían activas vuelven a ser operativas; TASK-008 no cambia esa reactivación ni desactiva automáticamente sus filas. La UI mostrará el horario activo para que ADMIN/RECEPTION lo revisen.

### 3.3 Invariantes de las cuatro RPCs de mutación

- LANGUAGE plpgsql SECURITY DEFINER, SET search_path = ''; todos los objetos calificados. Revocar EXECUTE de PUBLIC, anon y authenticated y concederlo sólo a authenticated en firmas exactas. No service role desde la aplicación.
- Rechazar auth.uid() nulo. Validar parámetros no nulos, día 1–7, hora en minuto exacto e inicio < fin; duración 5–480 múltiplo de 5. La DB vuelve a aplicar CHECK y GiST. Create fuerza is_active=true; update sólo cambia start_time/end_time de fila activa; deactivate sólo cambia is_active=false. Ninguna RPC acepta center_id/professional_center_id de destino distinto al par validado.
- Tomar lock advisory compartido sobre la misma clave de Center usada por las RPCs de administración existentes, de modo que cambios de disponibilidad entre sí sigan concurrentes y cambios de Center/membership/ProfessionalCenter se serialicen. Las rutas versionadas de estado de Center, membership y ProfessionalCenter usan lock exclusivo sobre esa clave; revalidar private.has_active_center_role(p_center_id, {ADMIN,RECEPTION}) después del lock. Leer ProfessionalCenter por id + center_id con FOR SHARE y exigir is_active. Para duration, tomar el lock exclusivo de Center como admin_update_professional_center, luego FOR UPDATE en ProfessionalCenter y comparar su updated_at monotónico. Reconfirmar este orden en el review SQL de A.
- Update/deactivate bloquean la fila Availability FOR UPDATE, filtrada por id + center_id + professional_center_id + is_active=true. No encontrada o ajena: error genérico RESOURCE_NOT_FOUND, sin revelar existencia. Comparar expected_updated_at exacto bajo lock; distinto: STALE_AVAILABILITY_STATE, sin retry automático. Un update sin cambio efectivo conserva fila y token; no-op de duración también conserva token. Deactivate es cambio efectivo.
- GiST es la garantía final de overlaps entre franjas activas, incluida la carrera de dos create/update sobre filas distintas. No hacer precheck de overlap como autoridad; si se añade para UX, la exclusión sigue mandando. Después de mutar, calcular el booleano de appointments fuera de horario dentro de la misma transacción. Un fallo revierte todo.
- Errores SQL contractuales: 22023 + mensaje propio para input inválido; 42501 para autorización; P0002 para recurso no disponible/ajeno; P0001 + token exacto para vínculo inactivo o stale; 23P01 sólo si el constraint es availabilities_no_active_overlap. El servidor mapea código + token/constraint conocidos, nunca texto SQL crudo. No distinguir recurso ajeno de inexistente en la UI.

## 4. Gate B — módulo servidor y Actions

Crear src/modules/availability/ con schemas, server, actions, componentes y tests cerca del código. Sin Route Handlers: son lecturas internas y mutaciones de la web.

- Schema Zod: UUID de Center/ProfessionalCenter/Availability; weekday entero ISO 1–7; HH:MM con 00:00–23:59 y segundos prohibidos; inicio < fin; expectedUpdatedAt ISO con offset; duración integer 5–480, multipleOf(5). El servidor no interpreta horas recurrentes con Date del navegador.
- Queries del módulo: listAvailabilityProfessionalCenters(centerId) usa la RPC mínima de contexto; getAvailabilityForProfessionalCenter(centerId, professionalCenterId) usa SELECT de availabilities con filtros center_id + professional_center_id + is_active=true y orden weekday/start_time, siempre con cliente de sesión. Comprobar que el ID solicitado aparece en el contexto autorizado antes de devolver filas; resultado faltante = notFound genérico. No usar admin client.
- Servicio de mutación: createAvailability, updateAvailability, deactivateAvailability y updateUsualAppointmentDuration validan, usan RPCs estrechas y devuelven DTOs mínimos. La Server Action crea cliente de sesión, valida FormData con Zod, reautoriza requireRole(centerId,[ADMIN,RECEPTION]), invoca el servicio y revalida la ruta exacta de detalle y el índice. Error mapping central del módulo a invalid interval, overlap, vínculo inactivo, acceso/rol, stale y error inesperado. Si el outcome de la RPC es incierto por error de red, pedir recarga antes de reintentar para evitar duplicados.
- No copiar el flujo CAS de Patients. Para create no hay token; para update/deactivate se usa expected_updated_at de la franja; para duración el token monotónico de ProfessionalCenter. El componente descarta estado local y hace router.refresh() ante stale. No actualizar optimistamente.
- Respuesta exitosa de create/update/deactivate incluye el booleano de advertencia. La Action sólo muestra el mensaje “Se guardó el horario. Hay turnos futuros fuera de la disponibilidad habitual; revisalos en Agenda cuando esté disponible” si es true. No crea enlaces a Agenda inexistente ni divulga citas.
